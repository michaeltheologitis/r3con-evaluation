================================================================================
Loong — benchmark reference (for a benchmarks / experiments write-up)
================================================================================
Wang, Chen, Fu, Liao, Zhang, Wu, Yu, Xu, Zhang, Luo, Li, Yang, Huang, Li,
"Leave No Document Behind: Benchmarking Long-Context LLMs with Extended Multi-Doc
QA", EMNLP 2024 (UCAS / Institute of Automation CAS / SIAT / Alibaba DAMO);
arXiv:2406.17419. Code+data: github.com/MozerWang/Loong and
github.com/AlibabaResearch/DAMO-ConvAI/tree/main/Loong. Our vendored question file
is loong.jsonl; the paper PDF sits beside this file.

This note is written to be paraphrased into a paper. It teaches the benchmark
end-to-end from BOTH the paper and the actual data — what it is, its four task
LEVELS and what reasoning each demands (with real examples pulled from the data),
the domain / language / length axes, why it is deliberately anti-RAG, how it is
scored, and what makes it hard. It closes with the deviations we made to run it in
our harness (§10, including one real upstream bug we fix) and exact sources (§11).


--------------------------------------------------------------------------------
1. THE BENCHMARK IN ONE PARAGRAPH — "leave no document behind"
--------------------------------------------------------------------------------
Loong measures whether an LLM can reason over MANY long documents at once when the
answer-supporting evidence is deliberately SCATTERED across them — so that ignoring
any single document produces a wrong answer. This is its whole thesis and what
separates it from prior long-context benchmarks: those either put the evidence in one
document and pad the rest with irrelevant NOISE (NIAH, RULER, distractor-extended
short-QA), which lets a model shortcut by finding the one needle; Loong instead makes
almost every document load-bearing. Each of 1,600 instances bundles ~11 real,
mostly-2024 documents from one of three professional domains (financial reports,
legal cases, academic papers), in English AND Chinese, and poses a question whose
answer requires locating, comparing, clustering, or chaining evidence pulled from
several of them. It is free-form generation graded by an LLM judge on a 1–100 scale
(reported as Avg Score + Perfect Rate). The paper's headline findings: even the best
2024 frontier models fail to reach a "passing" score (esp. on the strict Perfect
Rate), performance collapses as the context grows past a model's true (sub-claimed)
capacity, and — critically for us — adding RAG HURTS rather than helps, because the
evidence is too dispersed to retrieve a useful subset.


--------------------------------------------------------------------------------
2. WHAT'S IN IT — the raw material
--------------------------------------------------------------------------------
1,600 instances, each = an instruction + a question + a resolved bundle of documents
+ a gold answer (sometimes a JSON object or list, not a string). Concretely, from the
data:
  - DOMAINS (upstream `type`): financial reports 700, legal cases 500, academic
    papers 400. Documents are real and mostly from 2024 (SEC/cninf filings, China
    Judge Online rulings, arXiv papers), collected for timeliness + low contamination.
  - LANGUAGES: English 695, Chinese 905 — and language is entangled with domain:
    financial is the ONLY bilingual domain (EN 295 + ZH 405); academic papers are
    EN-only (400); legal cases are ZH-only (500). So "EN" ≈ papers + US filings and
    "ZH" ≈ Chinese filings + Chinese law — a method that is language-sensitive (e.g.
    NER, tokenization) must route per the `language` metadata.
  - SIZE: 2–54 documents per instance (mean ~10.2, median 6); instance token length
    (tiktoken) ranges ~11K to ~336K, median ~90K. Loong dials length by adding MORE
    real documents, never noise (§5) — so a longer instance is a harder search, not a
    padded one.
  - Each instance also carries its own upstream `prompt_template` with
    {instruction}/{question}/{docs} slots (a baseline that reproduces Loong's own
    prompt assembly can use it via get_prompt_template).


--------------------------------------------------------------------------------
3. THE FOUR TASK LEVELS (rising difficulty) — with real examples
--------------------------------------------------------------------------------
The core axis is the task LEVEL (upstream `level`, the harness `task`), of rising
difficulty; each decomposes reasoning differently. The paper further splits levels
2–4 into 10 named SUB-TASKS, but the sub-task label is NOT in the data (only the four
levels are), so treat sub-tasks as descriptive. Counts + examples are read from the
data.

  LEVEL 1 — SPOTLIGHT LOCATING (250 instances). The atomic case: the evidence sits in
    exactly ONE of the many documents; the others are same-domain, similar-semantics
    DECOYS. Tests pure long-range knowledge localization / search.
      financial (EN): "What is the Basic Earnings Per Share of General Enterprise
        Ventures, Inc.?" → "-$0.04".
      legal (ZH): "案由是'执行案由-先予执行'的判决文书是哪一篇?" (which single judgment
        document has cause-of-action X?) → 《判决文书10》.

  LEVEL 2 — COMPARISON (300). Evidence is distributed across MULTIPLE documents;
    locate the dispersed values and correlate/compare them. Sub-tasks: Sequential
    Enumeration (list all values of an attribute, in order), Extremum Acquisition
    (max/min across docs), Range Awareness (all objects meeting a numeric/conceptual
    range).
      financial (ZH, extremum): "'交易性金融资产' 最高的公司是哪一个？" (which company has
        the highest trading financial assets?) → 迈克生物.
      financial (EN, extremum): "Which company has the highest non-current assets?"
        → HARTE HANKS (from CIRTRAN / HARTE HANKS / GRESHAM ... spread over docs).

  LEVEL 3 — CLUSTERING (641, the largest level). Aggregate multi-source information:
    extract relevant data from many docs, THEN integrate/group it by a criterion.
    Answers are structured (a map of group → members). Sub-tasks: Report Integration
    (group financial-report evidence into buckets), Citation&Reference (EN papers:
    find a paper's citations + references among candidates), Case Classification (ZH
    law: bucket judgments by cause of action).
      financial (EN, report integration): "categorize the companies by 'Total Shares
        Outstanding' into high (≥20M) / medium (10–20M) / low (<10M)" → {"high
        shares": ["CLEARONE INC"], "medium shares": [], "low shares": ["BIOETHICS
        LTD", "Dominari Holdings Inc."]}.
      paper (EN, citation&reference): question = a paper title ("OpenMoE: An Early
        Effort on Open Mixture-of-Experts...") → {"Reference": ["# TinyLlama..."],
        "Citation": ["# Lory: Fully Differentiable MoE..."]}.
      legal (ZH, case classification): classify all judgment docs into 7 given causes
        of action → {cause: [《判决文书…》, ...]}.

  LEVEL 4 — CHAIN OF REASONING (409). Multi-hop reasoning along a logical/temporal
    pathway across documents. Sub-tasks: Temporal Analysis (trend of an attribute over
    time), Citation Chain (EN papers: infer a linear citation ordering), Link the
    Links (ZH law: pair each judgment's facts with its verdict), Solitaire (ZH law:
    match causes to judgments then infer a sequence).
      financial (temporal): "从2023年到2024年,'一年内到期的非流动负债'呈现什么变化趋势?列出各季度
        数据" → a narrative-plus-figures answer (increased 3.29B → 17.85B).
      paper (EN, citation chain): the QUESTION IS EMPTY — the whole task lives in the
        instruction ("construct a citation chain from the provided papers") → an
        ORDERED list of paper titles. (All 130 empty-question instances are exactly
        this sub-task — a baseline must fall back to the instruction alone, no
        dangling question.)
      legal (ZH, link the links): "阅读以上判决文书，我将给你若干份判决结果：{…}" — match each
        judgment DOCUMENT to its correct VERDICT → {《判决文书1》: "判决结果5", ...}. This
        is the sub-task whose verdict field must be withheld from the input, and where
        we fix an upstream leak (§10).

Difficulty ordering the paper reports: models do best on Spotlight Locating (single-
doc evidence, least confusable) and worst on Comparison + Clustering (multi-source
inference); Chain of Reasoning is fine in short contexts but collapses as length grows
(evidence overflows the effective window).


--------------------------------------------------------------------------------
4. THE AXES (all filterable in get_task_ids)
--------------------------------------------------------------------------------
Four orthogonal axes, all read from the data and exposed as metadata:
  - `task` (level 1–4) — the reasoning type above (250 / 300 / 641 / 409).
  - `domain` (financial / legal / paper) — 700 / 500 / 400.
  - `language` (en / zh) — 695 / 905; entangled with domain per §2.
  - `set` (length tier 1–4) — the context-length bucket, §5.
The analysis report hides the raw `length` (a continuous per-instance token count —
a finer-grained `set`) and the redundant `task_name`, and relabels `set`/`task` with
human names. Sub-tasks are not an axis (not tagged in data). NB: `language` matters
for a method-vs-benchmark story — the EN half is papers + US filings, the ZH half is
Chinese filings + all of legal; a legal result is necessarily a ZH result.


--------------------------------------------------------------------------------
5. WHY IT'S ANTI-RAG (the "leave no document behind" property, quantified)
--------------------------------------------------------------------------------
The design goal is dispersed evidence, and it has a direct consequence for retrieval
baselines. The paper explicitly tested Embedding RAG (OpenAI + BGE embeddings, top-k
5/10/30/50, chunk 1024) on GPT-4o and Qwen2-72B and found it does NOT improve overall
Loong performance and NOTABLY DECLINES it. Why: because evidence is spread evenly
across documents, answering needs a comprehensive read of the whole bundle; RAG
retrieves a top-k SUBSET, fragmenting context and dropping evidence the task needs.
RAG helps ONLY on the sparse-evidence Spotlight Locating level (and on ultra-long
Set4, where a strong-context model would otherwise truncate). A strong long-context
LLM beats RAG here; a weak one isn't rescued by it. This is the paper's basis for
claiming Loong "reliably assesses long-context modeling" — and for us it means the
retrieval/graph baselines (graphrag, linearrag, arag, raptor, readagent, memagent)
are EXPECTED FOILS on Loong versus direct-llm; that gap is the measurement, not a bug.
It is the sharpest benchmark in the harness for the RAG-vs-long-context question.


--------------------------------------------------------------------------------
6. THE LENGTH / SCALING DIMENSION
--------------------------------------------------------------------------------
The four length SETS (context-size tiers) are, from the data: Set1 10–50K (323
instances), Set2 50–100K (564), Set3 100–200K (481), Set4 200–250K (232, though some
instances run to ~336K). Length is increased by CONCATENATING more real documents of
the same task, so the same reasoning is tested at growing scale. The paper's "scaling
law of context window" finding: model accuracy deteriorates monotonically as the set
grows, and — importantly — models degrade WITHIN their claimed window (GPT-4o and
Qwen2-72B, both 128K-class, already drop in the 50–100K band), revealing an
"ineffective zone" where the usable context is well below the advertised window. Only
Gemini-1.5-pro (trained on 1000K) stayed robust. For our purposes: `set` is the axis
to stratify a per-iteration subset by (with `task`), so length and task-type effects
stay visible while judge cost is bounded.


--------------------------------------------------------------------------------
7. HOW IT'S SCORED (LLM judge, 1–100, Avg Score + Perfect Rate)
--------------------------------------------------------------------------------
Judge-only, no exact match (free-form generation, structured/JSON golds). An LLM judge
rates the model's answer 1–100 against the gold on two rubric criteria — (a) Accuracy
& Hallucinations (semantically consistent; numbers and ORDER must be right; no
fabrication) and (b) Completeness (covers all key points of the gold). Two metrics
roll up from the ratings: AVG SCORE (mean rating) and PERFECT RATE (fraction scoring
exactly 100) — the latter is the stricter, headline-honest metric (the paper stresses
even top models have low Perfect Rate). The harness marks this with PERFECT_SCORE=100,
which flips the analysis report from accuracy to Avg Score + Perfect Rate. Our judge
is JUDGE_MODEL (gpt-5.4-mini) with the rubric VERBATIM from upstream but delivered as
structured output (a `rationale` then an int `rating`) instead of upstream's `[[score]]`
text-parse; the paper used a GPT-4 judge on a 0–100 scale (see §10 for the small
prompt-plumbing changes). An empty answer earns the floor (1) with no paid judge call.


--------------------------------------------------------------------------------
8. WHAT THE PAPER FOUND (for a results / related-work section)
--------------------------------------------------------------------------------
Seven long-context LLMs (128K–1000K windows), temperature 0, GPT-4 judge:
  - OVERALL: Gemini-1.5-pro best (Avg 55.37 / Perfect Rate 27%), then GPT-4o (53.47 /
    26%); open-source (Qwen2-72B-128K, GLM4-9B-1000K) trail. No model reaches a
    "passing" bar, and Perfect Rate is low across the board — long-context multi-doc
    reasoning is far from solved.
  - BY TASK: Spotlight Locating easiest; Comparison + Clustering hardest (multi-source
    inference); Chain of Reasoning good short, collapsing long.
  - BY LENGTH: monotone decline with set size; degradation inside the claimed window
    (the "ineffective zone" / scaling-law observation).
  - RAG: does not help, usually hurts (§5).


--------------------------------------------------------------------------------
9. POSITIONING (vs other long-context benchmarks)
--------------------------------------------------------------------------------
The paper's Table 1 positions Loong as the only benchmark hitting all of: multi-doc
tasks, broad length sets, contamination avoidance, realistic scenarios, HIGH EVIDENCE
DISPERSION, and multilingual. Its foils:
  - NIAH / RULER / distractor-extended short-QA — long only via irrelevant NOISE, with
    CENTRALIZED single-document evidence → a search-a-needle surface test, shortcuttable.
  - LongBench / LooGLE / L-Eval / Marathon / InfiniteBench — realistic but mostly
    short (avg ~5–25K) and/or single-document, so they don't stress cross-document
    dispersion.
Loong's niche is realistic, contamination-light, bilingual, TRULY-long (median ~90K,
up to ~336K) MULTI-document QA with the evidence scattered on purpose. Within OUR
harness it is the archetype "leave no document behind" per-instance multi-doc
benchmark (its computation-heavier cousin is CorpusQA); direct-llm (raw full context)
is the strong baseline and the retrieval/agent methods are the foils to measure
against it.

10. HOW WE USE IT, AND WHAT WE CHANGED (deviations from upstream)
--------------------------------------------------------------------------------
We faithfully mirror upstream's document resolution (src/utils/prompt.py:get_content)
and vendor the question file byte-for-byte; the deviations (full ledger in CHANGES.md):
  (1) BUG FIX — the level-4 legal verdict LEAK (the only behavioral change, and it
      matters). The "match each judgment document to its verdict" sub-task (113
      instances) hands the model the case bodies plus a shuffled list of verdicts to
      match; the verdict (`result`) MUST be withheld from each document or the answer
      is in the input. Upstream tries to withhold it but checks the wrong field — it
      guards on the marker being in `instruction`, but the marker only ever appears in
      `question` (verified first-hand: 113 questions vs 0 instructions). So upstream's
      guard NEVER fires, every legal doc is emitted as content+verdict, and the gold
      leaks verbatim — the task becomes solvable by string-matching, not legal
      reasoning. (StructRAG vendored this code unchanged, so its published Loong
      numbers inherit the leak.) We check `question`, withholding the verdict for
      exactly those 113 instances; all other legal items (incl. the 66 L4 "Solitaire"
      match-to-category items) keep content+result, faithful to upstream. A ~3% residual
      leak remains where a judgment BODY narrates its own disposition — a data property
      we don't rewrite.
  (2) FULL SCOPE — we load all 1,600 (EN + ZH); the upstream starting point was
      English-only (695). A coverage choice; no instance is altered. `languages=`
      selects.
  (3) DETERMINISTIC DOC ORDER — upstream optionally shuffles + length-truncates the doc
      string per prompt; we return docs in the instance's `doc` order (reproducible,
      and legal's positional 《判决文书N》 titles + the gold references are keyed to it).
      A `shuffle_doc` field exists in the data; we do not use it.
  (4) JUDGE — gpt-5.4-mini (not GPT-4), rubric verbatim but structured-output (no
      [[score]] text-parse), rubric sent as a system message preceding the data, and
      the {docs} slot dropped from the judge's question (it grades against the gold,
      not the sources). Language-agnostic (multilingual model, gold JSON-encoded with
      ensure_ascii=False), so ZH is graded as-is.
  (5) FILENAME ENCODING — upstream's macOS `doc.zip` stores ZH financial filenames as
      UTF-8 bytes without the zip UTF-8 flag → mojibake under `zipfile`; we recover the
      real names on extract (cp437→utf-8). Contents untouched.
  Wiring: Loong is a per-instance multi-doc benchmark (get_documents → the bundle, no
  get_corpus), wired into every baseline — direct-llm, graphrag, structrag, arag,
  linearrag, readagent, rlm, codeact, raptor, memagent, claude-code. Empty-question
  instances (L4 paper citation-chain) compose to the instruction alone.
