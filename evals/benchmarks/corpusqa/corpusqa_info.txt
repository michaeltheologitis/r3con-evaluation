================================================================================
CorpusQA — benchmark reference (for a benchmarks / experiments write-up)
================================================================================
Lu, Li, Shi, Shen, Yan, Huang, "CorpusQA: A 10 Million Token Benchmark for
Corpus-Level Analysis and Reasoning", arXiv:2601.14952 (Tongyi Lab, Alibaba Group;
MIT). Data on Hugging Face; the paper PDF sits beside this file. Our vendored surface
is the offset index over the (gitignored, lazily-fetched) tier files.

This note is written to be paraphrased into a paper. It teaches the benchmark
end-to-end from BOTH the paper and the actual data (the wired 1m tier) — what it is,
the analytical question TYPES and what computation each demands (with real examples
pulled from the data), how the ground truth is programmatically guaranteed, the
domain / language axes, why it is deliberately anti-RAG, how it is scored, and what
the paper found. It closes with the deviations we made to run it in our harness (§11)
and exact sources (§12).


--------------------------------------------------------------------------------
1. THE BENCHMARK IN ONE PARAGRAPH — corpus-level analysis
--------------------------------------------------------------------------------
CorpusQA asks a model to answer an ANALYTICAL question that can only be answered by
reading and COMPUTING over a whole repository of documents at once — "how many
companies reported negative operating cash flow?", "list the top 3 by revenue",
"what is the total/average/median of X across all N filings?". Its defining property
is HIGH EVIDENCE DISPERSION: the answer-critical facts are not in a few chunks but
one-per-document across dozens-to-hundreds of documents, so producing the answer
requires holistic reading + statistical aggregation + precise arithmetic, not
retrieval of a relevant snippet. This deliberately breaks RAG's sparse-retrieval
assumption (the paper's headline: standard RAG "collapses entirely"). To make grading
trustworthy at this scale, the gold answers are NOT written by humans or an LLM — they
are PROGRAMMATICALLY COMPUTED: each document is schema-extracted into structured
key-values, aggregated into one global data table, and the question is executed
against it as SQL (NL2SQL), so the gold is a verifiable number / entity-list /
string. It is Loong's computation-heavy cousin (Loong was our loader's template):
same "leave no document behind" spirit, but the reasoning is quantitative analysis
over structured facts rather than locating/comparing text. The full benchmark scales
to 10M tokens across four length tiers; WE WIRE ONLY THE 1M TIER (Set2 — 329
instances, avg ~905K tokens).


--------------------------------------------------------------------------------
2. WHAT'S IN IT — the raw material (the wired 1m tier)
--------------------------------------------------------------------------------
Each instance = an instruction (the "Output requirements" block) + a natural-language
analytical question + a per-instance bundle of real documents + a programmatic gold.
From the wired 1m data (329 tasks):
  - DOMAINS (4): financial_en 83, financial_zh 83, education_en 82, real_estate_en 81.
    The document sources are real, table-rich filings:
      • financial_en — US SEC Form 10-Q quarterly filings (25 docs/instance, the
        LARGEST — ~5M+ chars per bundle).
      • financial_zh — Chinese A-share Q1-2025 quarterly reports (90 docs/instance).
      • real_estate_en — US Census "Monthly New Residential Construction" releases, a
        time series of monthly housing statistics (34 docs/instance).
      • education_en — university statistics (IPEDS-style: enrollment, faculty,
        degrees, class sections; 34 docs/instance).
    n_docs is FIXED per domain (25 / 90 / 34 / 34) — the corpus is a fixed set per
    domain, and "1M" is the token budget, hit with different doc counts + sizes.
  - LANGUAGE is DERIVED from domain: only financial_zh is Chinese (83 ZH); the other
    246 are English. So a language-sensitive method routes off `language`, but ZH is
    isolated to one financial domain (unlike Loong, where ZH also covers all of legal).
  - SIZE: the 1m tier averages ~905K tokens/instance (per the paper's Table 2), though
    actual sizes vary by domain (the 25 SEC 10-Qs are far larger than the 90 short
    Chinese quarterlies). Documents are real PDFs parsed to Markdown, kept only if
    >10,240 tokens AND rich in statistical tables (the pipeline's two-stage filter).
  - The full benchmark is FOUR parallel length tiers — Set1 128K (~92.5K tok), Set2 1M
    (~905K), Set3 4M (~3.71M), Set4 10M (~7.84M), each 329 instances — the same task
    structure re-rendered at growing corpus scale. We wire only Set2/1m (§11).


--------------------------------------------------------------------------------
3. THE ANALYTICAL QUESTION TYPES — with real examples
--------------------------------------------------------------------------------
The reasoning is quantitative analysis over the dispersed facts. The recurring shapes,
read off the actual data:
  - FILTER (single-condition select → a list): "List all universities with more than
    1,000 part-time instructional faculty members." → ["Temple University", "San
    Francisco State University", "Columbia University"].
  - RANK / TOP-K (order by an attribute → a list): "List the top 3 companies with the
    highest total revenues." → ["ALPHABET INC CLASS C", "CHEVRON CORP", "EATON PLC"];
    "Which company has the largest total assets?" → ["ALPHABET INC CLASS C"] (a
    single-element list).
  - STATISTICAL AGGREGATION (count / sum / mean / median over ALL docs → a number):
    "How many companies reported negative net cash from operating activities?" → 6;
    "What is the total sum of cash and cash equivalents for all companies combined?" →
    52336782000.0; "2025年第1季度末所有公司总资产的平均值是多少?" (average total assets
    across all companies) → 14024624637.56; "median value for not-seasonally-adjusted
    total housing units authorized" → 279650.0.
  - CROSS-DOCUMENT ARITHMETIC / ARGMAX over a series: "Find the month with the largest
    number of housing units in 2-to-4-unit buildings authorized." → ["2023-08"].
  Every one of these REQUIRES a large fraction of the bundle: a sum/average/count/max
  is wrong if even one document's value is missed — this is the anti-RAG property made
  quantitative.

The paper (Appendix B) further grades questions by DIFFICULTY (Easy / Medium / Hard),
though this field is EMPTY in the released rows, so it is NOT an axis we can filter on
(see §7). The ladder is still worth citing for what "Hard" means here:
  - EASY — basic aggregation / single-dimension: "List the top 5 universities by total
    enrollment"; "Find universities with >1,000 part-time faculty"; "Rank top 10 by
    transfer students."
  - MEDIUM — numerical calc + multi-condition: "Calculate the admission rate for each
    university"; "Which universities have a graduation rate above 90% AND fewer than
    5,000 undergraduate students?"; grouped comparisons.
  - HARD — custom metrics + multi-step reasoning: "For all universities with a
    first-year admission rate below 50%, compute the average six-year graduation rate,
    then find those >15 percentage points above it"; or an "advanced metric
    construction" like flag companies where X1·1.2 + X2·1.4 + X3·3.3 < 1.8 with each Xi
    a ratio of balance-sheet lines. These require the model to build a formula and
    evaluate it per entity across the corpus.

GOLD-ANSWER TYPES (1m data): a list of entities (207), a number (75), a short string
(21), or an INTENTIONAL EMPTY LIST "[]" (26 = "no rows matched the filter"). The empty
list is an anti-hallucination signal like LongHealth's abstention: the correct answer
is "none", and a model that invents entities to fill the list fails.


--------------------------------------------------------------------------------
4. WHY THE GOLD IS TRUSTWORTHY — the schema→table→NL2SQL pipeline
--------------------------------------------------------------------------------
The paper's third design principle is "guaranteed factual grounding", and it is what
lets CorpusQA pose questions too hard for an LLM to annotate reliably. The six-stage
pipeline (paper Fig 2): (1) collect real PDFs → Markdown, filter to long + table-rich;
(2) SCHEMA EXTRACTION — an ensemble of three SOTA models (Gemini 2.5 Pro, GPT-4.1,
Qwen-Max) each extract key-values per document, keeping only MAJORITY-CONSENSUS values
(discarding docs that don't produce agreement); (3) generate queries from
human-authored templates, LLM-paraphrased for diversity; (4) aggregate every
document's extracted JSON into ONE global data table (rows = entities, cols =
attributes); (5) NL2SQL — translate the query to SQL, EXECUTE it against the table →
the ground-truth answer; (6) assemble the instance by concatenating the ORIGINAL
full-text documents as the context. So the model sees raw unstructured text, but the
gold was computed on a structured backend — "100% accurate and logically derived".
Reported extraction fidelity: 94.13% (education_en) / 98.97% (financial_zh) human-
verified consistency, and a review of disagreements found the model extraction correct
every time. This is the key differentiator from Loong (LLM+human annotation) and from
RAG benchmarks (human-written multi-hop questions).


--------------------------------------------------------------------------------
5. THE OUTPUT-REQUIREMENTS CONTRACT (the block that MUST reach the model)
--------------------------------------------------------------------------------
Because the gold was computed by SQL, the question ships with an "Output requirements"
block that encodes the SEMANTICS the gold assumes — it is task specification, not
decoration, and MUST be given to the model (our loader un-bakes it as the
`instruction`). Verbatim, it says: (1) the answer must be one of — a list of strings
(incl. "[]"), a single short string, a number (2 decimals, no units), or a percentage
(2 decimals); (2) dates as "YYYY-MM"; (3) IF MULTIPLE FILES CONFLICT for the same
item, use the value from the LATEST file (a disambiguation rule the SQL applied); (4)
place the final answer as "The answer is: xxx". Two of these bind grading directly:
the "The answer is:" contract is what the judge's extract_answer keys on (§8), and the
latest-file conflict rule is why a naive reader that averages conflicting values
disagrees with the gold. The system persona is just "You are a professional data
analyst, please answer the question accurately."


--------------------------------------------------------------------------------
6. WHY IT'S DELIBERATELY ANTI-RAG (and what IS resilient)
--------------------------------------------------------------------------------
CorpusQA is engineered so retrieval cannot work: because a correct sum/average/rank
needs EVERY document's contribution, retrieving a top-k SUBSET structurally cannot
gather the globally-dispersed evidence. The paper demonstrates this directly (Table
4, all on Gemini-2.5-Pro): RAG trails a memory agent at every scale and COLLAPSES as
the corpus grows — Avg accuracy 55.85 (128K) → 17.38 (1M) → 2.43 (4M) → 1.20 (10M),
with the worst cases flagged where the number of retrieved chunks was smaller than the
number of documents, "making accurate answers impossible". MEMORY-AUGMENTED agents
(fixed-size memory folded over the stream) are far more resilient (67.58 → 44.95 →
22.14 → 11.13) but still far from solving it. For our harness this sets clear
expectations: the retrieval/graph baselines (graphrag, linearrag, arag, raptor,
readagent) are the SHARPEST foils in the suite on CorpusQA — a top-k retriever cannot
compute a corpus-wide aggregate — while the programmatic-scan family (rlm, codeact,
claude-code, which can write code to read/compute over every document) and memory
(memagent) should be the resilient methods. direct-llm is a truncation foil once the
1M bundle exceeds the window. That contrast is the measurement.


--------------------------------------------------------------------------------
7. THE AXES
--------------------------------------------------------------------------------
  - `domain` — the report MERGES the bilingual financial split (financial_en +
    financial_zh → one "financial" bucket, language suffix dropped) → three report
    buckets (education / financial / real estate); the RAW 4-way domain still drives
    get_task_ids(domains=…), and financial_en vs financial_zh stays recoverable by
    `language` (or by n_docs: 25 vs 90).
  - `language` — en / zh, derived from domain (only financial_zh is zh).
  - `set` — the context-length tier, ALWAYS "1m" (the only wired tier). A bare
    get_task_ids() returns all 329.
  - `n_docs` — the per-instance document count (a domain-fixed constant here).
  NOT an axis: the paper's Easy/Medium/Hard DIFFICULTY — the row `type` field is the
  empty string in every released row (verified across all four domains), so it carries
  no signal and the loader does not surface it. A reader expecting to stratify by
  difficulty cannot, on the released data.


--------------------------------------------------------------------------------
8. HOW IT'S SCORED (0/1 answer-equivalence judge)
--------------------------------------------------------------------------------
Judge-only, 0/1, plain accuracy (no PERFECT_SCORE — unlike Loong's 1–100). Because the
gold is a number / entity-list / string that can be written many equivalent ways
(282 vs 282.0, ordering, units, phrasing), exact match is unreliable, so an LLM
"ORM" (Output Reward Model) judge decides EQUIVALENCE. The flow, reproducing upstream
src/eval.py: first run extract_answer on the model's reply (take what follows "The
answer is: ", the enforced contract), then ask the judge whether that extracted answer
is equivalent to the gold → 1/0. An empty extracted answer is 0 with no paid call
(and never matches even a "[]" gold). Our judge is JUDGE_MODEL (gpt-5.4-mini) with the
equivalence rubric VERBATIM from upstream but delivered as structured output (an
`explanation` then a boolean `equivalent`) instead of upstream's [[YES]]/[[NO]]
text-parse; upstream used DeepSeek-V3. Language-agnostic, so financial_zh grades as-is.


--------------------------------------------------------------------------------
9. WHAT THE PAPER FOUND (for a results / related-work section)
--------------------------------------------------------------------------------
  - BASE LLMs (Table 3): at 128K, strong — GPT-5 82.02, Gemini-2.5-Pro 80.19; at 1M,
    SUBSTANTIAL degradation even for million-token models — Gemini-2.5-Pro best at
    50.73, Gemini-2.5-Flash 37.31, MiniMax-M1 collapsing to 11.63. Only top-tier models
    show partial resilience at the million-token scale.
  - RAG COLLAPSES, MEMORY RESISTS (Table 4, §4.3): the central result (§6 above).
  - SUPERHUMAN SCALE (Table 5): a human expert scores 75% at 128K but only 50% at 1M
    (33% timed out at a 90-min cap) and 0% at 4M/10M (100% timeout / gave up) — the task
    becomes "demonstrably superhuman", while a memory agent stays operational (25% at
    4M, 16.7% at 10M).
  - REASONING > INSTRUCTION (Appendix A): thinking models beat their instruct
    counterparts by a wide margin (Qwen3-235B-Thinking 78.08 vs Instruct 61.41) — the
    benchmark is sensitive to reasoning ability, not just alignment.
  - TRAINING UTILITY (§4.4): fine-tuning on data from the same synthesis pipeline
    improves CorpusQA AND generalizes to LongBenchV2 + FRAMES.


--------------------------------------------------------------------------------
10. POSITIONING (vs other benchmarks) + our harness role
--------------------------------------------------------------------------------
The paper's Table 1 positions CorpusQA as the only benchmark that is simultaneously
up-to-10M-length, reasoning-intensive, controllable-context, HIGH-evidence-dispersion,
and multilingual. Its foils:
  - InfiniteBench / LongBenchV2 — recall/reason within a SINGLE concatenated long text,
    not integration across many discrete documents.
  - Loong / FanOutQA — multi-document, but "fewer than a dozen documents" whose total
    context fits a modern window, so not a true corpus-level (hundreds of docs)
    challenge. (CorpusQA is Loong scaled up + made computation-heavy with programmatic
    gold.)
  - FRAMES / CRAG — RAG benchmarks premised on sparse retrieval, which CorpusQA's high
    dispersion invalidates.
Within OUR harness, CorpusQA is the computation-heavy extreme of the "leave no document
behind" family (Loong's cousin, MINTEval's peer): the strongest test of whether a
method can synthesize globally-dispersed structured evidence. direct-llm is a
truncation foil at 1M; retrieval/graph methods are the sharpest foils; the
code/memory methods (rlm, codeact, claude-code, memagent) are the ones expected to
have a chance.

11. HOW WE USE IT, AND WHAT WE CHANGED (deviations from upstream)
--------------------------------------------------------------------------------
We vendor nothing multi-GB; the connector reads the lazily-fetched tier file through a
byte-offset index. The deviations:
  (1) 1M-ONLY. The full benchmark is four tiers (128K / 1M / 4M / 10M); we wire ONLY
      the 1m tier (Set2, 329 instances). Rationale: 128K is too small to be
      interesting; 4M/10M fit no context window and are not hosted on Hugging Face (our
      sole mirror). So SETS == {"1m"} and a bare get_task_ids() returns all 329.
  (2) TASK-ID KEYS ON THE FILE TIER, NOT THE ROW'S `set` FIELD (a real bug we fix).
      Upstream ships every row with set == "128k" even inside the 1m file; keying task
      ids on row["set"] made every id "@128k" and (when 128k was also wired) silently
      served 128k content for 1m tasks. We key on the FILE the row came from (@1m), so
      the id resolves to the right tier. (Index version v2.)
  (3) UN-BAKE THE FROZEN PROMPT. Each row's `prompt` is the fully-assembled [system,
      user] chat request upstream sent, with the documents, the # Question: marker, and
      the # Output requirements block glued together. We split it back into
      (instruction, question, docs): docs on the "# Document N:" headers, the question
      from the row's own field, and the instruction = the output-requirements block
      (which MUST reach the model — §5). The "The answer is:" contract is kept so the
      judge's extract_answer works.
  (4) BYTE-OFFSET INDEX. The 1m file is ~1 GB; loading it per subprocess would OOM. On
      first use we build a small index (metadata + each row's byte offset); enumeration,
      metadata, gold, and judging read the cheap index, and only get_task / get_documents
      seek+read one row's prompt.
  (5) JUDGE — gpt-5.4-mini (not DeepSeek-V3), rubric + extract_answer verbatim,
      structured-output instead of [[YES]]/[[NO]] text-parse.
  Wiring: CorpusQA is a per-instance multi-doc benchmark (get_documents → the bundle,
  no get_corpus), wired into every baseline — direct-llm, graphrag, structrag, arag,
  linearrag, readagent, rlm, codeact, raptor, memagent, claude-code. Each poses the
  query as question + the output-requirements instruction block.
